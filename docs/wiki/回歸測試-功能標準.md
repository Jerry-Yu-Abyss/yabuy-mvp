# 回歸測試 ②：功能標準（Check List）

← 回 [[Home]]　｜　另一份：[[回歸測試-已知事故]]

> ## 這份文件的定位
>
> **本文件是「功能標準」的：從系統應有的行為出發，逐項定義期待結果，形成完整 Check List。**
>
> 它回答的問題是：**「系統該有的功能，現在是不是真的正常？」**
>
> | | [[回歸測試-已知事故]]（①） | 這份（②功能標準） |
> |---|---|---|
> | 問題 | 舊 bug 有沒有復發？ | 系統該有的功能正不正常？ |
> | 來源 | 實際發生過的事故 | 系統應有的行為規格 |
> | 指令 | `npm run check:bugs` | `npm run check:func` |
> | 覆蓋 | 窄而深，只守已知地雷 | 廣而完整，40 項逐條驗收 |
>
> **兩份都要跑**（`npm run check` 一次跑完）：①確保沒退步，②確保功能真的能用。

---

## 一、怎麼使用

```bash
npm run check:func                        # 跑自動項目 + 顯示完整進度
npm run check:func -- --list              # 只列 Check List，不執行
npm run check:func -- --pass C-03 "備註"   # 記錄某項人工驗證通過
npm run check:func -- --fail C-03 "原因"   # 記錄某項人工驗證失敗
npm run check:func -- --reset C-03        # 清除某項紀錄
```

腳本會輸出四類狀態，並在最後給出**進度條**與**下一步該做什麼**：

| 標記 | 意義 |
|---|---|
| `[自動 ✓]` / `[自動 ✗]` | 腳本自動驗證的結果，每次執行都會重新驗 |
| `[人工 ✓]` / `[人工 ✗]` | 人工驗證後用 `--pass` / `--fail` 記錄的結果，存在 `scripts/functional-results.json` |
| `[ 待測 ]` | 尚未驗證，會一併顯示「期待結果」與「誰能執行」 |

**進度會持久保存**（結果檔案納入版控），所以中斷後可以接續，也看得出哪些項目是什麼時候驗的。

> ⚠️ **重要**：改動程式碼後，受影響的項目要用 `--reset` 清掉舊紀錄重驗。
> 舊的通過紀錄不代表改動後仍然正常。

## 二、執行者分類（決定工作流順序）

Check List 的每一項都標註了「誰能執行」，這決定了**你和模型的分工**：

| 標記 | 意義 | 誰做 |
|---|---|---|
| **自動** | 腳本直接驗，不需要人 | 模型執行 `npm run check:func` 即可 |
| **免登入** | 需操作瀏覽器，但不用登入 | 模型可自行完成 |
| **需登入** | 需操作瀏覽器且要登入狀態 | **你先登入**，之後模型可自行完成 |
| **需雙帳號** | 需要買賣雙方兩個帳號互動 | 需要你協調兩個帳號 |
| **需人眼** | 視覺／體感，機器判斷不了 | 只能你來 |

**建議的工作流順序**：

1. `npm run check:func` → 自動項目立即有結果（4 項）
2. 模型完成「免登入」項目（1 項）
3. 你在瀏覽器登入 → 模型接手完成「需登入」項目（19 項）
4. 你準備兩個測試帳號 → 一起完成「需雙帳號」項目（16 項，交易主流程都在這）

### C. 交易邏輯（15 項）

建議**照 C-01 → C-15 的順序**執行，因為它們大致對應一筆交易的生命週期：

```
  → 安全交易(C-08~09) → 掃碼(C-10) → 議價(C-11)
  → 成交(C-12) → 評價(C-13)
```

## 四、自動化項目在檢查什麼

這 4 項每次執行都會重新驗證，是**零成本的護欄**：

**A-02 公開統計**
匿名 POST 呼叫 `getPublicStats`，驗證回傳兩個非負整數。這同時證明了：Cloud Function 有部署、未登入訪客真的看得到統計、且函式沒有意外要求驗證。

**D-01 索引覆蓋（靜態）**
掃描 `src/` 所有 `.vue`/`.js`，用括號配對取出每個 `query(...)` 呼叫，解析出 `where` 與 `orderBy` 欄位，再比對 `firestore.indexes.json` 是否有相符的複合索引。
**為什麼重要**：缺索引的查詢**只有在使用者實際觸發那個畫面時才會噴錯**，平常完全看不出來，是最容易漏掉的一類問題。

**D-02 索引實際可執行（動態）**
直接對 Firestore REST API 發出與前端**完全相同**的查詢。D-01 只證明「索引有宣告」，這項證明「索引真的部署到線上了」——兩者不同，宣告了但忘記 `firebase deploy --only firestore:indexes` 是常見情況。

> ⚠️ 這裡的查詢條件必須與前端**完全一致，包含 where 的數量**。
> 少送一個 `where` 就變成另一組索引需求，測出來的 400 是假警報。
> （撰寫時就踩過：`Book.vue` 有 `category` + `status` 兩個 where，只送一個會誤報。）

**D-03 業務常數（靜態）**
驗證 8 個關鍵商業規則常數沒有被誤改：交易時段 6–18 時、安全交易前置 10 分鐘、取消上限 3 次 / 30 天、成交金額上限 10000、賣家改期 1 次、買家改期 2 次。
**為什麼重要**：這些數字被改動不會有任何錯誤訊息，但會直接改變交易規則。

## 五、新增案例時

1. 在 `scripts/check-functional.mjs` 的 `CASES` 陣列新增，**這是單一事實來源**
2. 必填：`id`／`area`／`title`／`expect`（期待結果要具體到可判定對錯）／`runner`
3. 能自動化就給 `fn`，回傳 `[boolean, 說明字串]`
4. 更新本文件的總覽表格

**期待結果的寫法**：要寫成「可以判定對錯」的敘述，不要寫「功能正常」這種無法驗證的說法。

- ❌ 「收藏功能正常」
- ✅ 「favorites 新增一筆（userId=本人），該商品從卡片堆消失，收藏頁看得到」
