# 已知問題

← 回 [[Home]]

整理這次統整過程中發現、但**尚未修正**的技術債，供之後排優先順序。

## 1. `Heart.vue` 分頁不可達

`App.vue` 的頂部導覽列圖示曾把愛心（收藏）換成地圖（見對話記錄「Mailbox換圖示」那次改動），但 `activeTab === 'heart'` 這條路由沒有清掉——目前**沒有任何按鈕**會設定 `activeTab = 'heart'`。

- 功能本身沒壞：收藏清單仍可從 `User.vue` 的「喜愛」分頁使用
- 但 `Heart.vue`（265 行）連同它的 Firestore 監聽變成死碼，且 `App.vue` 裡 `activeTab !== 'heart'` 的判斷式也是死條件
- 建議：確認產品需求後，要嘛移除 `Heart.vue` 相關程式碼，要嘛在 `List.vue` 選單加一個入口

→ 詳見 [[導覽架構]]

## 2. Storage 規則不在版本控制內

`firestore.rules` 已納入版控（見 [[驗證與權限]]），但 `storage.rules` 仍不存在於這個 repo，`firebase.json` 也沒有 `storage` 區塊——代表圖片上傳（商品照/頭像/廣告圖）的存取權限是直接在 Firebase Console 手動編輯的。

- 沒有 code review 紀錄可查規則什麼時候改過、為什麼改
- 新環境/新開發者無法從 clone 這個 repo 重建出完整的安全設定，也無法從 repo 判斷目前的實際風險
- 建議：`firebase deploy --only storage` 需要的 `storage.rules` 補上並納入版控

## 3. Firebase Emulator：Auth／Firestore 已就緒，Storage 仍缺

**2026-08-15 更新——這條已解決一半，剩下的部分如下。**

已完成：`firebase.json` 有 `emulators` 區塊（auth 9099／firestore 8080／UI 4000），
`npm run emu` 可啟動，`npm run emu:seed` 造種子資料，`npm run dev:emu` 讓前端連本機。
新增 `npm run check:trade`（49 項）驗交易狀態機與安全規則，見 [Harness Engineering.md](../../Harness%20Engineering.md) 的 F5。

**仍然缺的：Storage emulator。** 圖片上傳（商品照／頭像／廣告圖）在本機仍會打正式
Storage，因為 `storage.rules` 根本不在版控內（見下方第 2 條），沒有規則檔就沒辦法
讓 emulator 載入。這兩條要一起解。

⚠️ 前置需求：Firestore emulator 是 JVM 程式，**機器上必須有 JDK**。沒有 Java 時
`npm run emu` 起不來，`check:trade` 會自動 skip（退出 0）而不是讓 commit 閘門擋死。

## 4. 名不符實的 PWA

README 與 `Landing.vue` 都把專案定位成 PWA，並有「加入主畫面」教學影片，但：

- `public/` 沒有 `manifest.json`
- `main.js` / `index.html` 沒有註冊任何 service worker

嚴格來說目前只是「可以加到手機主畫面的一般網頁」，不是符合標準的可安裝 PWA（沒有離線快取、沒有 install prompt 觸發條件）。

## 5. 建置產物偏大

`npm run build` 持續出現這個警告：

```
(!) Some chunks are larger than 500 kB after minification.
dist/assets/index-*.js   ~769 kB (gzip ~259 kB)
```

單一 chunk，沒有做 code-splitting；另外 `src/assets/map/AU-Map-01.jpg` 約 4MB，直接原圖打包進 `dist/`，`MapPage.vue` 沒有壓縮或延遲載入。

## 6. `index.html` 還是預設模板

`<title>Vite</title>`，從未改成 `YaBuy`——瀏覽器分頁標題、社群分享預覽都會顯示錯誤名稱。

## 7. `Deal.vue` 除錯訊息量偏大

`Deal.vue` 的 `syncStep()` 等關鍵函式留了大量 `console.log/warn`（含完整訂單物件），正式站也會印出。內容不含密碼等機敏資訊，但會洩漏商品/交易細節到瀏覽器主控台。

## 8. `audit_logs` 可被任何登入者偽造，且無人能刪

`firestore.rules` 的 `audit_logs` 是 `allow create: if request.auth != null`——沒有任何欄位驗證。任何登入者都能寫入任意內容的稽核紀錄：把操作者寫成別人、把時間寫成過去，或大量灌入垃圾把真紀錄淹沒。而 `update, delete: if false` 讓這些垃圾連管理員都清不掉。

- 這是整份規則裡唯一符合「injection」語意的一項（log injection）
- 建議：至少強制 `actorId == request.auth.uid`、`createdAt == request.time`、`category`／`level` 限定列舉值；刪除權開給管理員，或乾脆改由 Cloud Function 以 Admin SDK 寫入，前端完全不給 create

## 9. `users` 的 create 沒有欄位白名單

`allow update` 的第 (1) 條擋掉了本人竄改 `isAdmin`／`isFounder`／`ratingSum`／`ratingCount`，但 **`allow create` 沒有任何欄位限制**。還沒有 Firestore 文件的帳號（`backfillUserDocs` 的存在證明這種人確實有）可以自己建一份帶 `isAdmin: true, isFounder: true` 的文件。

- **不構成提權**：規則的 `isAdmin()` 讀的是 token custom claim，`User.vue`／`Admin.vue` 也都走 `getIdTokenResult().claims.admin`
- 但 `Admin.vue` 的用戶清單是直接讀 Firestore 欄位渲染徽章，所以這個人會在後台顯示成「👑 創辦人」，誤導管理者
- 建議：create 時比照 update 加上 `!request.resource.data.keys().hasAny([...])`

**部分已處理**：`expireCount` / `expirePeriodStart`（面交爽約紀錄）已加入 create 的禁止清單——那條額度會擋住發起新交易，若能「先建一份乾淨的文件」就等於憑空清空紀錄。`isAdmin` / `isFounder` 仍未納入，上述誤導後台的問題依舊成立。
