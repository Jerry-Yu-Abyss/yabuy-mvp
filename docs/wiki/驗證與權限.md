# 驗證與權限

← 回 [[Home]]　｜　寫入哪個欄位見 [[資料模型]]

分成兩套完全獨立的機制：**信箱驗證**（決定能不能交易/上架）與**管理員權限**（決定能不能進後台）。

## 信箱驗證（`verify.js`）

單一事實來源，三態：

| 狀態 | 條件 |
|---|---|
| `google` | `emailVerified === true` 且 `providerData` 含 `google.com` |
| `email` | `emailVerified === true`，非 Google 登入 |
| `not_yet` | `emailVerified === false`（**不論**是否曾綁過 Google——這點曾是 bug，見下方修正記錄）|

### 關鍵函式

- `resolveVerifyStatus(fbUser)` —— 純函式，由 Firebase user 物件推導三態
- `ensureVerified(fbUser)` —— 交易/上架前的即時守門：先 `fbUser.reload()` 拉最新 `emailVerified`，reload 成功才回寫 Firestore（失敗的狀態不可信，不拿來寫資料庫）
- `syncVerifyStatus(fbUser, status)` —— **唯一**允許寫入 `users.verify` 的地方；規則：
  1. 文件不存在就不寫（建檔交給 `Landing.vue`/`User.vue` 的 `upsertUserDoc`）
  2. 狀態沒變不浪費一次寫入
  3. **禁止降級**：`isVerified(current) && !isVerified(status)` 時直接跳過——避免本機快取的舊 `emailVerified` 把資料庫裡已經正確的 `email`/`google` 打回 `not_yet`
- `sendVerificationThrottled(fbUser)` —— 重寄驗證信，**60 秒節流**（時間戳存 `localStorage`，key 為 `yabuy:verifyMailAt:{uid}`）。原因：Firebase 每寄一封新驗證信就會讓前一封的連結失效，短時間內連續觸發會讓使用者點到「已過期」的舊連結
- `blockUnverifiedForTrade(fbUser, toastFn, {resend, action})` —— 各頁交易/上架入口共用的攔截函式，未通過時顯示 toast 並視冷卻狀況決定要不要重寄

### 誰呼叫這套邏輯

| 檔案 | 用途 |
|---|---|
| `Landing.vue` / `User.vue` 的 `upsertUserDoc` | 建檔/登入時寫入初始 `verify`（含防降級）|
| `App.vue` | 每次 `onAuthStateChanged` 觸發時呼叫 `ensureVerified(user)`（背景執行，不 await）|
| `TradeModal.vue` `Home.vue` `Funnel.vue` `Book.vue` `Heart.vue` `User.vue` | 發起交易前呼叫 `blockUnverifiedForTrade` |
| `Cam.vue` | 上架前呼叫，`action: '發布商品'`（訊息文案跟著換）|
| `User.vue` 的 `refreshVerifyState` | 進到「我的」頁時主動 reload 一次，避免橫幅停在別裝置驗證前的過期狀態 |

## 管理員權限（Firebase Custom Claims）

不經過 Firestore 規則判斷身分，而是 **Custom Claims**（`admin: true` / `founder: true`），由唯一一支 Cloud Function 設定：

`functions/src/index.ts` → `addAdminRole`（Callable Function）

```
呼叫者未登入                → unauthenticated
呼叫者非創辦人且非管理員      → permission-denied
不帶 email（bootstrap 自己）：
  └ 呼叫者是創辦人 → 設自己 admin+founder；否則 permission-denied
帶 email（授權他人）：
  └ 只有創辦人能執行；創辦人本人的權限不可被取消
```

- **創辦人 email 寫死在程式碼**：`reso950211zxc@gmail.com`（`FOUNDER_EMAIL` 常數）
- `users/{uid}.isAdmin` / `.isFounder` 只是**鏡像**，方便 `Admin.vue` 的用戶列表顯示徽章，實際權限判斷永遠以 Custom Claims 為準（前端讀 `idTokenResult.claims.admin`）
- `Admin.vue` 的「確認我的管理員權限」按鈕就是呼叫 `addAdminRole` 不帶 `email` 參數，用於創辦人首次 bootstrap

## Firestore 規則：讀寫範圍收斂到「本人／當事人／管理員」

`firestore.rules`（已版控）原本大多數 collection 只檢查「有沒有登入」，沒有檢查「是不是本人的資料」。這代表任何登入者都能讀寫別人的訂單、收藏、面交訊息，`users.email` 甚至連登入都不用就能整批撈走。收斂後：

| Collection | 讀 | 寫 |
|---|---|---|
| `orders` | 只有 `buyerId`／`sellerId`／管理員 | 建立限 `buyerId == auth.uid`；改動限當事人／管理員；不開放刪除 |
| `favorites` | 只有 `userId` 本人 | 建立限本人；不開放更新（只有新增/刪除） |
| `messages` | 只有該筆 `orders.orderId` 的買家/賣家（`isOrderParty()` 回頭查 `orders`） | 同左，且 `senderId` 必須是本人；更新只開給「推遲請求的收件者」（見下），不開放刪除 |
| `audit_logs` | 只有管理員 | 任何登入者可建立（一般使用者發起交易時會寫一筆），不開放更新/刪除（唯讀稽核） |
| `users` | 需登入（原本 `if true`，任何人不登入都能撈全站 email） | 不變 |
| `products` | 不變（公開可讀） | `create` 新增驗證 `sellerId == auth.uid`，避免冒名替別人上架 |

**`messages` 的更新為什麼要開一條縫**：「希望推遲至 X 點面交」是一則等對方回覆的訊息，收件者得能把 `requestStatus` 從 `pending` 改掉，原本的 `update: if false` 做不到。放行範圍鎖到最小——必須是訂單當事人、**不能是發送者本人**（否則可以自問自答單方面改時間）、只准動 `requestStatus` 一個欄位（否則能先發「推遲到 15:00」，等對方同意後再偷改 `proposedTime`）、起點限 `pending`（回覆過就定案，不能翻案）。這四條在 `npm run check:trade` 第 7 節都有對應的 403 測試。

**三種額度，三種防護強度**：

| 額度 | 記在哪 | 誰寫 | 擋得住嗎 |
|---|---|---|---|
| 推遲面交時間（買賣各 1 次） | `orders.buyerDelayUsed` / `sellerDelayUsed` | 前端 | ✅ `delayUsedOk()`：只能 false → true，且只有本人能立自己那一支 |
| 面交爽約（30 天 3 次） | `users.expireCount` / `expirePeriodStart` | **只有 Cloud Function** | ✅ 前端 update／create 都被擋，發起交易時由 `orders.create` 的 `notExpireBanned()` 把關 |
| 主動取消（30 天 3 次） | `users.cancelCount` / `cancelPeriodStart` | 前端 | ❌ 使用者可自行改回 0——見 [[新交易流程規格]] 的風險 1 |

爽約那一條之所以能做到，是因為它從頭就設計成「使用者碰不到自己的紀錄」：要扣的是**對方**的次數，前端本來就寫不了別人的 `users` 文件，所以只能放伺服器端，順勢也把本人竄改的路一起封死。

**連帶影響**：`Ranking.vue`（排行榜）原本直接在前端 `getDocs(collection(db,'orders'))` 撈全站原始訂單、在瀏覽器裡即時算聚合值——`orders` 收緊後這條路會被規則擋掉，因此改成呼叫新的 Cloud Function `getRankingStats`（`functions/src/index.ts`），由伺服器端用 Admin SDK 算好聚合數字才回傳，前端拿不到任何一筆原始訂單。`Indicate.vue`（管理端指標）因為只有管理員能進入，靠規則的 `isAdmin()` 例外繼續直接讀，不受影響。

**同樣模式再用一次**：`Landing.vue`（未登入的首頁/登入頁）要顯示「X 位同學已加入、X 件商品已循環」這種信任指標，但訪客根本還沒登入，讀不到收緊後的 `users`/`orders`。用同一套「後端算聚合值」的做法新增 `getPublicStats`——這支刻意**不檢查 `request.auth`**（本來就設計給未登入的人用），也**不接受任何呼叫參數**，用 Firestore 的 `count()` 聚合查詢（伺服器端甚至不會把任何一份文件內容載進記憶體），保證無論是誰、用什麼方式呼叫，能拿到的東西永遠只有兩個整數，沒有第三種資料可以被挖出來。
