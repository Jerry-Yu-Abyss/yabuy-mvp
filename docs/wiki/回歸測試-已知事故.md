# 回歸測試 ①：事故驅動（給模型讀）

← 回 [[Home]]　｜　另一份：[[回歸測試-功能標準]]

> ## ⚠️ 這份文件的定位
>
> **本文件是「事故驅動」的：每一條都回溯自這個專案真實發生過的 bug，不是通用最佳實踐、也不是完整的功能測試。**
>
> 它只回答一個問題：**「以前壞過的地方，這次有沒有又壞了？」**
>
> | | 這份（①事故驅動） | [[回歸測試-功能標準]]（②功能標準） |
> |---|---|---|
> | 問題 | 舊 bug 有沒有復發？ | 系統該有的功能正不正常？ |
> | 來源 | 實際發生過的事故 | 系統應有的行為規格 |
> | 指令 | `npm run check:bugs` | `npm run check:func` |
> | 覆蓋 | 窄而深，只守已知地雷 | 廣而完整，逐項 Check List |
>
> **兩份都要跑**：這份確保沒退步，另一份確保功能真的能用。

這份文件的目的是**收斂模型的產出**：把這個專案實際踩過的坑固化成可驗證的斷言，讓後續的模型改完程式碼就能自我校準，不需要人類每次重新指出同樣的問題。

新增條目前請先確認它擋得住某個實際踩過的坑，否則只是製造雜訊。

---

## 一、先跑自動化檢查

```bash
npm run check:bugs
```

- **退出碼非 0 就代表這次改動有回歸，修好之前不要宣告完成。**
- 只改了原始碼、還沒部署時用 `npm run check:bugs -- --local`（跳過所有網路檢查）。
- 這支腳本本身經過負面測試：故意改壞會 FAIL，不是永遠綠燈的裝飾品。

腳本已涵蓋（**不需要再手動確認這些**）：

| 層面 | 檢查內容 |
|---|---|
| Firestore 規則 | 以未登入身分實測 9 個 collection 的讀取狀態碼（該擋的 403、該公開的 200）|
| 商品資料 | 必要欄位、`status` 值域、`isBook` 與 `category` 一致性、價格為正、`sold` 必有 `soldAt` |
| 部署產物 | `<title>` 非預設、`apple-touch-icon`／`manifest` 標籤、PWA 圖示可取得、bundle 保留 `viewBox` |
| 原始碼 | 8 個寫入按鈕的防連點旗標位置、兩條 Google 登入路徑都建檔、`ensureVerified` 短路、SVGO 設定、規則未退回寬鬆版 |

## 二、腳本驗不到、必須自己判斷的

自動化只能守住「已知的、可機器判定的」部分。以下每次改動都要自己過一遍：

- [ ] **改了 `.vue` 的 `<style scoped>`？** 確認樣式沒有預期會影響其他元件——scoped 樣式**不跨元件**，父層定義的 class 子元件吃不到（見下方坑 1）。
- [ ] **新增了會寫入 Firestore 的按鈕？** 必須加防連點，並把新函式登記進 `scripts/check-known-bugs.mjs` 的 `GUARDS` 陣列，否則下次沒人守得住。
- [ ] **新增了 collection？** `firestore.rules` 一定要加對應規則（沒寫 = 全部 403），並把預期狀態碼加進腳本的 `RULE_EXPECTATIONS`。
- [ ] **改了跨使用者的聚合查詢？** 不可以在前端 `getDocs(collection(...))` 撈全站原始資料再自己算——要走 Cloud Function 在伺服器端算好聚合值（見坑 11）。
- [ ] **改了版面？** 用 `getBoundingClientRect()` 確認沒有水平溢出，不要只看截圖（見坑 4 與下方驗證技巧）。
- [ ] **需要登入才能測的功能？** 不能代替使用者登入，請明確告訴使用者哪一段沒驗到，不要含糊帶過。

## 三、這個專案踩過的坑

改到相關區域時必讀。格式：**症狀 → 根因 → 怎麼判斷**。

### 1. scoped 樣式不跨元件
**症狀**：把 `Home.vue` 的卡片內容抽成 `AdCard.vue` 後，按鈕樣式全跑掉。
**根因**：`<style scoped>` 只作用於該元件自己的 DOM，`Home.vue` 定義的 `.action-row`／`.vote-btn` 子元件完全吃不到。
**判斷**：抽元件時，把用到的 class 在新元件的 `<style scoped>` 內重新定義一份。

### 2. 防連點旗標設在 `await` 之後等於沒設
**症狀**：`Cam.vue` 已經有 `isUploading` 旗標，網路慢時連點仍會上傳多張圖、建立重複商品。
**根因**：旗標設在 `await requireVerified()` **之後**，那段網路請求期間按鈕仍是可按的。
**判斷**：旗標必須在**第一個 `await` 之前同步設定**。腳本會檢查已登記的 8 個進入點。

### 3. `updateDoc` 對不存在的文件會直接 throw
**症狀**：缺 Firestore 文件的孤兒帳號，去改個人資料只會跳「更新失敗」，無法自救。
**根因**：`updateDoc` 不會建檔，文件不存在就 reject。
**判斷**：不確定文件是否存在時，用 `setDoc(..., { merge: true })` 或先 `getDoc` 判斷。

### 4. flex／grid 的 `min-width: auto` 會撐爆版面
**症狀**：Landing 頁手機版第二個統計數字被切在螢幕外。
**根因**：新增的 flex 外層預設 `min-width: auto`，會撐到子項目的 max-content 寬度（橫向捲動的商品卡列約 825px），把整欄推出畫面。
**判斷**：包含橫向捲動容器的 flex／grid 子項目，記得加 `min-width: 0`。

### 5. SVGO 會拿掉 `viewBox` 造成圖示裁切
**症狀**：`.send-btn` 的圖示邊緣被切掉。
**根因**：`vite-svg-loader` 預設的 SVGO `removeViewBox` 外掛，會在 `viewBox` 剛好等於 `width`/`height` 時移除它；少了 `viewBox`，CSS 縮放時瀏覽器不會等比例縮放內容，而是直接裁切座標系。
**判斷**：這是**全站所有 `?component` 載入的 icon 共通**的風險，修在 `vite.config.js` 載入器層級，不要只改個別 svg。

### 6. 每次點擊都 `reload()` 會讓按鈕變遲緩
**症狀**：交易請求按鈕「感覺很卡」。
**根因**：`ensureVerified()` 每次都呼叫 `fbUser.reload()`（真實網路請求），而它被每次發起交易／上架前的守門呼叫。
**判斷**：`emailVerified` 只會 false→true 不會反向，已經是 `true` 就直接短路，不要再問伺服器。

### 7. Firestore 沒寫規則 = 全部 403
**症狀**：新加的 `messages` 功能完全讀不到資料。
**根因**：Firestore 預設拒絕，每個 collection 都要有明確的 `match` 區塊。
**判斷**：新增 collection 時，寫程式碼**之前**先補規則。

### 8. `cardStack` 每滑一張就整個重算
**症狀**：想讓廣告「每 10 個商品出現一次」，用陣列位置算永遠湊不滿。
**根因**：`Home.vue` 每次滑動都會 `updateCardStack()` 從頭重建陣列，相對位置每次都歸零。
**判斷**：跨重算的節奏要用**持續累加的計數器**（`swipedProductCount`），不能用當下陣列的索引。

### 9. 廣告滑掉後會被排回原位
**症狀**：廣告卡「怎麼滑都滑不掉」。
**根因**：滑掉後重算時，節奏與保底條件都沒變，同一則廣告又被排回同一個位置。
**判斷**：即時合成（不來自資料庫快照）的項目，被消化掉時要明確記錄（`dismissedAdIds`），重算時排除。

### 10. 同一則廣告在同一次重算裡被塞進兩個插槽
**症狀**：只上架 1 則廣告，卻在同一疊卡片裡撞見同一則廣告兩次，感覺像卡片壞掉/跑版。
**根因**：商品清單夠長、一次出現不只一個「每 10 個」觸發點時（例如 i=0 跟 i=10 都成立），`pickNextAd()` 沒有排除「這次 recompute 已經用過」的廣告，兩個插槽各自呼叫都選到同一則。
**判斷**：同一次重算裡，插槽之間要共用一份「已用過」的排除清單（`usedAdIds`），廣告池不夠大時晚到的插槽該空著，不能為了填滿每個插槽而重複塞同一則。

### 11. 同一件事有兩條路徑，只改一條
**症狀**：2026-07-09 起所有經 Landing 頁用 Google 註冊的人都沒有 Firestore 文件。
**根因**：`Landing.vue` 與 `User.vue` 各有一套 Google 登入，只有後者呼叫了 `upsertUserDoc`。
**判斷**：改動登入／交易／上架這類核心流程時，先 `grep` 確認**所有**入口都改到（例如 `signInWithPopup` 有兩處、`addDoc(collection(db,"orders")` 有五處）。

### 12. Cloud Function 的 Admin SDK 會繞過 Firestore 規則
**這是設計重點不是坑**：收緊規則後，跨使用者的聚合統計（排行榜、公開統計）改由 Cloud Function 用 Admin SDK 讀取——它不受 rules 限制，所以能算全站資料，但只回傳聚合後的數字，前端拿不到任何一筆原始資料。需要跨使用者統計時走這條路，不要放寬規則。

### 14. 測到模組本人，卻沒測到有人呼叫它
**症狀**：私訊過濾的三項自動測（C-23／C-24／C-25）全綠，但那只證明 `chatFilter.js` 判斷正確——`CannedChat.vue` 或 `can.js` 忘記呼叫它的話，測試照樣全過，聊天室卻能直接送出電話號碼。
**根因**：測試對象是「純函式」，斷點卻在「呼叫端有沒有接上」。這個缺口只有人工實機驗證才發現得了（2026-09-10 實機確認）。
**判斷**：把純邏輯抽成獨立模組時，除了測模組本身，另外加一條**靜態檢查確認呼叫端真的呼叫了**，而且要擋在真正寫入的那個函式裡（`can.js` 的 `sendChatMessage`），不是只看 UI 的 `disabled`——按鈕變灰擋不住 Enter 送出、貼上即送，或任何改了 UI 卻沒動送出邏輯的重構。已由 `check-known-bugs.mjs` 的 1-8 覆蓋。

### 13. Firebase 的 `apiKey` 公開是正常的
`src/firebase.js` 裡的 `apiKey` **不是密鑰**，前端 SDK 的 config 本來就會出現在每個瀏覽器裡。真正的防線是 Firestore 規則。不要把它誤判為安全漏洞去「修復」。

### 15. `admin.firestore.Timestamp` 執行期是 undefined，但 TypeScript 編得過
**症狀**：2026-09-10，`onOrderClosed` 在正式站上每一筆結束的訂單都拋 `TypeError: Cannot read properties of undefined (reading 'fromMillis')`，`chatPurgeAt` 從來沒被寫進去——「交易結束 24 小時後清除對話」從上線那天起就沒有生效過。
**根因**：`functions/src/index.ts` 用的是 modular import（`import {FieldValue} from "firebase-admin/firestore"`）。在這種風格下 `admin.firestore.Timestamp` 的**型別存在、執行期的值不存在**，所以 `tsc` 編得過、eslint 過、`firebase deploy` 也成功，要等真的執行到那一行才炸。同一個寫法在 `backfillUserDocs`（149／152 行）已經潛伏很久，只因為管理端一直只跑試跑而沒被觸發。
**判斷**：需要 `Timestamp` 就從 `firebase-admin/firestore` 具名匯入，比照既有的 `FieldValue`。更一般的教訓是：**Cloud Function 的錯誤不會讓部署失敗，也不會讓任何靜態檢查變紅**——它只出現在執行期的 functions log 裡。這個 bug 通過了 `check:code`、`check:prod`(23+8 全過)、tsc、以及部署，唯一抓到它的是 `check:trade` 第 9 節那條真的去讀 `chatPurgeAt` 有沒有被寫入的斷言。改動 trigger 一定要用 `npm run emu:fn` 跑過，不能只看部署成功。

## 四、驗證技巧（比肉眼看截圖可靠）

| 要驗什麼 | 怎麼驗 |
|---|---|
| 安全規則是否真的生效 | 直接 `curl` Firestore REST API，不帶任何憑證，看狀態碼——不需要登入就能測 |
| 改動有沒有真的進到線上 | `grep` 編譯後的 `dist/assets/index-*.js` 找關鍵字串 |
| 樣式是否與另一元件一致 | 用 `getComputedStyle()` 逐項比對，不要靠肉眼看縮圖 |
| 版面有沒有溢出 | `document.documentElement.scrollWidth > window.innerWidth` + `getBoundingClientRect()` |
| 快取造成看到舊版 | 網址帶 `?cb=<遞增數字>` 強制繞過 |
| Landing 頁擋住主畫面 | `localStorage.setItem('yabuy_landing_seen','1')` 後重整 |

## 五、工作流程約定

1. **改程式碼 → `npm run build` → `firebase deploy --only hosting` → 驗證 → 等使用者明確說 commit。**
   commit 與部署是分開的兩件事，**沒有被明確要求就不要 commit／push**。
2. 改到 `functions/` 要另外 `firebase deploy --only functions`；部署前會自動跑 lint + build，兩者都必須通過。
3. 改到 `firestore.rules` 要 `firebase deploy --only firestore:rules`。
4. **不能代替使用者登入**，任何情況都不行。需要登入才能驗的部分，明確說出來哪一段沒驗到。
5. 使用者說「我手動測試就好」時，不要再自己跑瀏覽器驗證，把結果交還給他。
6. commit 訊息用繁體中文，格式為 `動詞: 簡述`（例：`修復: ...`／`新增: ...`／`移除: ...`），內文說明根因而非只描述改了什麼。
