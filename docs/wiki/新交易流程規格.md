# 新交易流程規格（簡化版）

← 回 [[Home]]　｜　現行流程見 [[交易生命週期]]　｜　資料欄位見 [[資料模型]]

> **狀態：已實作（[[元件目錄|Mailbox.vue]] / [[元件目錄|Deal.vue]] / `can.js` / `TradePoints.js` / `DealTimeline.vue` / `CannedChat.vue`）。三個風險依需求方指示未處理，維持原樣記錄供之後參考。**
>
> **⚠️ 已知阻塞：罐頭訊息完全無法運作。** 正式站的 Firestore 規則是逐 collection 明確允許的清單（非本次協作才發現——這推翻了先前「一般使用者可讀寫全站任何 collection」的認知，那個結論只驗證過 `orders`/`users`/`products`），`messages` 從未被加入允許清單，讀寫一律 403 permission-denied。需要有 Firebase Console 存取權限的人加一條規則，不是程式碼能解決的。
>
> **⚠️ 未做的驗證：真實兩支裝置的即時互動。** 已用「同一帳號分飾買賣雙方」的合成訂單完整跑過一次 安全交易→掃碼→金額→完成，狀態機邏輯確認正確；但沒有測過兩個真人在各自裝置上同時操作的時序狀況（例如：即時看到對方按下按鈕、真的用手機相機掃 QR）。

## 一、與現行流程的差異

| 項目 | 現行（[[交易生命週期]]） | 新流程 |
|---|---|---|
| 交易前溝通 | 無，只能「改提案」改時間地點 | **罐頭訊息**即時對話框（新 `can.js`）|
| 取消 | 買家可無限次取消 | **一個月上限 3 次**，需記錄於 `users` |
| 進入面交 | 隨時可按「我抵達了」 | **交易時間前 10 分鐘**才開放「安全交易」按鈕 |
| 身分驗證 | 賣家出示 QR（內容＝`order.id`）、買家掃描 | **雙方各自掃描交易點的實體 QR**（地點編碼）|
| 驗證意義 | 證明「我跟這位交易對象在一起」 | 證明「我在這個地點」＋留存實際時間地點供糾紛調閱監視器 |
| 流程進度提示 | 無 | 頂部**時間線**標示目前位置 |
| 金額 / 評價 | 買家出價 → 賣家確認 → 評價 | **沿用不變** |
| 完成畫面 | 顯示成交金額 | 顯示**實際**地點、時間、金額 |

## 二、流程定義

```
① 預約（沿用 TradeModal）
   └ orders: status='pending' → 賣家接受 → status='accepted'
        │
② 信箱等待期（交易時間前）
   ├ 罐頭訊息：即時對話框，雙方可傳預設短語
   └ 取消交易：檢查當月次數 → 未達上限才可取消
        │        └ 達上限 → 提示「本月已取消 3 次」並擋下
        │
③ 時間閘門：距約定時間 ≤ 10 分鐘 → 開放「安全交易」按鈕
        │
④ 雙方各自按下「安全交易」
        │  （單方按下 → 顯示等待對方，不可前進）
        │
⑤ 全版面交易流程開啟（頂部時間線）
        │
⑥ 雙方掃描交易點實體 QR（地點編碼）
   └ 寫入 actualLocation / actualTime
   └ 畫面告知：系統已記錄實際時間地點，糾紛時可調閱該地點監視器
        │
⑦ 買家輸入實際成交金額 → 賣家確認　（沿用現行 price / seller-confirm-price）
        │
⑧ 雙方互評　（沿用現行 reviews 寫入 + users.ratingSum/ratingCount）
        │
⑨ 完成畫面：顯示實際地點、實際時間、實際金額
        │
⑩ 返回信箱
```

### 需要新增的資料

**`users/{uid}`** — 取消次數
| 欄位 | 型別 | 說明 |
|---|---|---|
| `cancelCount` | number | 當期已取消次數 |
| `cancelPeriodStart` | Timestamp | 當期起算時間，跨月重置 |

**`orders/{id}`** — 實際交易紀錄
| 欄位 | 說明 |
|---|---|
| `buyerSafeReady` / `sellerSafeReady` | 是否已按「安全交易」|
| `buyerScannedAt` / `sellerScannedAt` | 各自掃描實體 QR 的時間 |
| `actualLocationCode` | 掃到的交易點編碼 |
| `actualTime` | 實際完成掃描的時間（伺服器時間）|

**新 collection `tradePoints/{code}`** — 實體交易點
| 欄位 | 說明 |
|---|---|
| `name` | 顯示名稱（圖書館、鳥籠…）|
| `hasCamera` | 是否有監視器涵蓋 |
| `active` | 是否啟用 |

**新 collection（或 `orders` 子集合）`messages`** — 罐頭訊息
| 欄位 | 說明 |
|---|---|
| `orderId` `senderId` `text` `createdAt` | 只允許預設短語，不開放自由輸入 |

### 新檔案

- `can.js` — 罐頭訊息清單與傳送邏輯（比照 [[元件目錄|verify.js]] 的「單一事實來源」寫法，讓 Mailbox 與未來其他頁面共用）

## 三、實作前必須解決的三個風險

### 🐛 風險 1：取消次數限制寫在前端＝形同虛設，且會算錯

**問題**：`users` 文件目前是使用者自己 `updateDoc` 寫入的（[[元件目錄|List.vue]] 改個人資料就是這樣做）。若把 `cancelCount` 放在同一份文件、由前端遞增，使用者只要用 REST API 把它改回 0 就能無限取消——這在本次協作中已實測確認：一般登入者可直接讀寫 Firestore。

**第二層問題**：若用「讀出 count → +1 → 寫回」，兩次快速取消會讀到同一個舊值、各自寫入 3，計數少算（lost update）。

**失敗情境**：使用者連按兩次取消，`cancelCount` 從 2 只加到 3 而非 4；或使用者發現後直接改寫欄位歸零，限制完全失效。

**避免方式**：
1. 計數用 `increment(1)` 原子操作（[[元件目錄|Deal.vue]] 的評價彙總已經是這樣寫）
2. **限制必須由 Firestore 安全規則或 Cloud Function 強制**，不能只靠前端判斷。目前 repo 內沒有 `firestore.rules`（見 [[已知問題]]），這件事得一併處理
3. 「跨月重置」不要用前端當下時間判斷，改以 `cancelPeriodStart` 與 `serverTimestamp()` 比對

### 🐛 風險 2：時間閘門用裝置時間，且按鈕不會自己解鎖

**問題 A（可繞過）**：`orders.time` 目前存成 `"2026-08-05 14:00"` 純字串、**不含時區**。`new Date("2026-08-05 14:00")` 會依裝置本地時區解析，不同裝置算出的「還剩幾分鐘」不一樣；使用者把手機時間調快，也能提早解鎖「安全交易」。

**問題 B（畫面不更新）**：若寫成
```js
const canStartSafeTrade = computed(() => Date.now() >= startAt - 10 * 60 * 1000);
```
這個 computed **沒有任何響應式依賴**（`Date.now()` 不是 ref），時間到了也不會重算——使用者會盯著一顆永遠不開的按鈕，直到切分頁或有其他狀態變動才突然解鎖。這與本次已修好的三個「畫面卡住」問題屬同一類。

**失敗情境**：使用者準時抵達交易點，時間已過 13:50，但按鈕仍是灰的，重整頁面才恢復正常。

**避免方式**：
1. 存 `orders.startAt` 為 Firestore `Timestamp`（絕對時間），不要只留字串
2. 前端建立 `const now = ref(Date.now())` 搭配 `setInterval` 每 10–30 秒更新，讓 computed 有依賴可追蹤；`onUnmounted` 記得 `clearInterval`
3. 真正的閘門判斷（寫入 `safeReady`）交由規則／Function 以伺服器時間驗證，前端只負責顯示

### 🐛 風險 3：實體 QR 是靜態碼＝可預先翻拍，且失去「雙方在場」的證明

**問題**：實體 QR 若只編一個固定的地點代碼（如 `LIB-01`），任何人拍過一次就能在任何地方掃出同樣結果。這會直接推翻新流程主打的安全承諾——系統記錄「圖書館，14:00」，但兩人其實各自在宿舍完成，糾紛時調閱監視器只會發現沒有畫面。

**第二層問題（設計退化）**：現行流程是賣家出示含 `order.id` 的 QR、買家掃描，這證明了**兩人此刻在同一個地方、且對象正確**。改成雙方各自掃同一個地點碼後，這層「彼此在場」的驗證就消失了——兩人可以在不同時間各自去圖書館掃一次，系統一樣判定成交。

**失敗情境**：買家在宿舍用截圖掃碼、賣家隔天才到圖書館掃碼，訂單仍標記為「圖書館面交完成」，事後糾紛無從查證。

**避免方式（擇一或並用）**：
1. **加上時間窗約束**：兩人的掃描時間差需在合理範圍內（如 5 分鐘），否則不予通過——這用伺服器時間比對 `buyerScannedAt` / `sellerScannedAt` 即可，成本最低
2. **保留點對點驗證**：掃地點碼之外，仍保留現行「掃對方 QR」一步，地點碼只用來標記地點，不取代身分驗證
3. 若要真正防翻拍，需動態碼（交易點放置的裝置定時輪替），成本高，MVP 階段建議用方式 1

## 四、實作時的一致性要求

⚠️ 本次協作已連續修好三個「畫面與資料庫狀態不同步」的 bug（見 commit `0c3a799`）。新流程的步驟更多，同類問題只會更容易發生。硬性要求：

- **時間線 UI 與流程步驟必須從同一份 Firestore 狀態推導**，不可另外維護一份 index。
- 任何「我方已完成、等對方」的中間狀態，都必須有明確的等待畫面，不可讓畫面停在原處。
- 每個非同步送出動作，成功路徑也要解除 loading（用 `finally`）。
