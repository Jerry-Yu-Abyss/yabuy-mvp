# 自訂網域與寄信設定

← 回 [[Home]]　｜　寄信邏輯本體見 [[驗證與權限]]　｜　部署指令見 [[部署與環境]]

## 背景

Firebase Auth 內建的驗證信／密碼重設信，預設由 `noreply@yabuy-2026a.firebaseapp.com` 寄出。這個網域是**全世界所有 Firebase 專案共用**的，沒有獨立信譽，常被信箱系統直接歸類垃圾郵件。

解法：改用自己的網域 `yabuy-tw.com` 寄信，並透過 [Resend](https://resend.com) 當 SMTP 轉送服務。這牽涉**兩套完全獨立的綁定**，中途踩到的坑幾乎都是把兩者搞混、或是被中間的 DNS 代理擋住：

| 綁定 | 目的 | 設定位置 |
|---|---|---|
| Hosting 自訂網域 | 讓 `https://yabuy-tw.com` 直接開啟 YaBuy 網站 | Firebase Console → Hosting |
| Auth 自訂 SMTP | 讓驗證信／密碼重設信從 `noreply@yabuy-tw.com` 寄出 | Firebase Console → Authentication → 範本 → SMTP settings |

兩者都需要在 DNS 供應商（此專案用 **Cloudflare**）加對應紀錄，但紀錄內容、目的完全不同，不要以為做完一個另一個就會自動生效。

## 一、Hosting 自訂網域

Firebase Console → Hosting → 新增自訂網域 → 輸入 `yabuy-tw.com`，依序拿到並加入：

1. **TXT** 紀錄（`hosting-site=yabuy-2026a`）——證明網域擁有權，Firebase 驗證用，跟真正的網站服務無關
2. **A** 紀錄（`199.36.158.100`）——真正把網域指向 Firebase 伺服器的紀錄

驗證通過、DNS 生效後，Firebase 自動簽發 SSL 憑證，Hosting 頁面該網域狀態會顯示「已連結」。

## 二、Auth 自訂 SMTP（Resend）

1. Resend 後台 → Domains → Add Domain → 輸入 `yabuy-tw.com`，拿到 SPF（TXT）、DKIM（TXT/CNAME）紀錄加進 Cloudflare，等狀態變 **Verified**
2. Resend 後台 → API Keys → 建立一把 Sending access 權限的 key（**只顯示一次，要立刻複製**）
3. Firebase Console → Authentication → **範本**分頁（不是「設定」分頁，這兩個很像但功能不同）→ 右上角找到 SMTP settings 入口 → 啟用並填入：

| 欄位 | 值 |
|---|---|
| 寄件者電子郵件地址 | `noreply@yabuy-tw.com` |
| SMTP 伺服器主機 | `smtp.resend.com` |
| SMTP 伺服器通訊埠 | `587` |
| SMTP 帳戶使用者名稱 | `resend`（固定字串，不是帳號名） |
| SMTP 帳戶密碼 | Resend 的 API key |
| SMTP 安全模式 | TLS |

寄件者網域一定要跟 Resend 驗證過的網域一致，否則 Resend 會直接拒寄。

## 三、踩到的 Bug

### Bug 1：Cloudflare Proxy 擋住 Hosting 的 A 紀錄

**症狀**：Firebase Console 的 Hosting 頁面已經顯示 `yabuy-tw.com` 狀態「已連結」，但實際打開網址卻是 Firebase 回傳的 `Site Not Found` 頁面（提示訊息第三點：「This is a custom domain, but we haven't finished setting it up yet.」）。

**排查方式**：直接對網域做 DNS 查詢，比對實際解析出來的 IP 跟 Firebase 給的 A 紀錄是否一致：

```bash
nslookup yabuy-tw.com 8.8.8.8
```

結果解析到 `172.67.182.209` / `104.21.18.176`——這是 **Cloudflare** 的 IP，不是 Firebase 的 `199.36.158.100`。

**根因**：Cloudflare 的 DNS 紀錄有個「Proxy status」（介面上是一朵**橘色雲朵**圖示）。開啟時（Proxied），所有連線會先進 Cloudflare 的邊緣節點再轉發，訪客實際連到的是 Cloudflare 的 IP，不是我們填的 origin IP。Firebase Hosting 需要**直接**看到訪客連線才能完成 SSL 憑證簽發跟正確回應內容，中間被 Cloudflare 代理攔截就會一直卡在「未完成設定」的狀態，即使 Firebase 後台顯示已連結也一樣（Firebase 只確認了 A 紀錄「存在」，不代表流量真的能直達）。

**修法**：Cloudflare DNS 頁面，把 `yabuy-tw.com` 的 A 紀錄從「Proxied」（橘色雲朵）切成「**DNS only**」（灰色雲朵）。切換後 Cloudflare 只單純回答 DNS 查詢，不再攔截轉發。

**這條規則只套用在 Hosting 用的 A 紀錄**——Resend 那邊給的 MX／TXT（SPF、DKIM）紀錄本來就不是給瀏覽器連線用的，維持 DNS only 是正常預設值，不受這個 bug 影響。

### Bug 2：修好後不同 DNS 解析器結果不一致（DNS 傳播延遲）

**症狀**：關掉 Cloudflare Proxy 後，立刻查詢還是查到舊結果。

**排查方式**：同時查兩個不同的公用 DNS 解析器：

```bash
nslookup yabuy-tw.com 1.1.1.1   # Cloudflare 自家 DNS
nslookup yabuy-tw.com 8.8.8.8   # Google 的 DNS
```

查到 `1.1.1.1`（Cloudflare 自己的解析器，同時也是這個網域的權威 DNS）已經回傳正確的 `199.36.158.100`，但 `8.8.8.8`（Google）還停在舊的 Cloudflare IP。

**根因**：Cloudflare 身為這個網域的權威 DNS，自己的解析器最先反映改動；其他公用解析器（Google、各家 ISP、使用者裝置本身）都各自快取了修改前的結果，要等快取的 TTL 過期才會重新查詢拿到新答案。這不是設定錯誤，純粹是 DNS 傳播的正常現象，通常幾分鐘到最多數小時內會自動收斂。

**處理方式**：沒有辦法強制加速別人的 DNS 快取，只能等待，或用不同網路環境（例如手機關 WiFi 改行動網路）繞開本地已快取的舊結果做初步驗證。

## 最終正確的 Cloudflare DNS 紀錄

| Name | Type | Content | Proxy status |
|---|---|---|---|
| `yabuy-tw.com` | A | `199.36.158.100` | **DNS only**（灰雲朵，必須關代理） |
| `yabuy-tw.com` | TXT | `hosting-site=yabuy-2026a` | DNS only |
| `send.yabuy-tw.com` | MX | Resend 的 feedback-smtp 位址 | DNS only |
| `send.yabuy-tw.com` | TXT | `v=spf1 include:amazonses...`（SPF） | DNS only |
| `resend._domainkey.yabuy-tw.com` | TXT | DKIM 公鑰 | DNS only |
